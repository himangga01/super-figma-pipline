## Build and start

Use Node.js 24 and `pnpm@11.24.0`, from `service/` in a separate development working copy:

```powershell
corepack pnpm install --frozen-lockfile --ignore-scripts
corepack pnpm build
node packages/mcp/dist/daemon-entry.mjs
```

The daemon runs in the foreground; stop it with `Ctrl+C`. Run CLI commands from another terminal in `service/`. For MCP clients, configure `node` with the absolute path to `packages/mcp/dist/index.mjs` instead. See the [repository overview](../README.md#development-setup).

## Service web portal

After building and starting the daemon, start the login-free web portal in another terminal:

```powershell
corepack pnpm portal:start
```

Open `http://127.0.0.1:4310` in Google Chrome. The portal edits and saves workflows, shows live stages and events, and sends explicit approval, context, submission, validation and application requests through the service's public control client. It runs locally on the same PC as the daemon. The current execution bridge supports the ordered source, requirements, generation, validation and output stages. Draft branches can be edited but cannot execute yet. A coding agent still obtains the service lease and submits implementation files; starting a workflow does not launch a background coding model.

`SFP_PORTAL_PORT` changes the web port; `SFP_CONTROL_PORT` selects the daemon port. `SFP_PORTAL_STATE_ROOT` selects a dedicated portal store. For a separately configured daemon state, the portal process must use the same `LOCALAPPDATA` and `SFP_STATE_ROOT` values as that daemon. These are local process settings; private control credentials stay on the backend. Native Chrome connection approval remains manual.

Run `corepack pnpm portal:test` for the portal backend, frontend model/API and required service-owned Google Chrome checks. See the [portal verification records](../docs/testing/2026-10-11-web-portal/review.md) for dated results and actual live-acceptance limits.

## Four implementation cases

| Request                                  | Resolution                           | Scope                                                                      |
| ---------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------- |
| New service                              | Reference supplied: C3; otherwise C4 | Inherits the resolved strategy                                             |
| Existing legacy service                  | C2                                   | All relevant UI, API, backend, data, auth, job and integration changes     |
| New service based on explicit references | C3                                   | An independent portal using relevant reference patterns and service layers |
| New service without a reference          | C4                                   | Frontend only, with honest local demo adapters                             |

The three upstream toolkits are pipeline foundations. They are never automatically treated as business-service references.

## Start a portal plan

From the `service` directory, after building:

```powershell
node packages/cli/dist/index.mjs portal plan --case new --yes
node packages/cli/dist/index.mjs portal plan --case legacy --target C:\services\legacy --yes
node packages/cli/dist/index.mjs portal plan --case new-reference --reference C:\services\reference --out C:\services\new-portal --yes
node packages/cli/dist/index.mjs portal plan --case new-blank --stack react-vite --yes
```

The supplied Figma file `4IBhv1d8hEclifZQrOYxHS`, initially node `0:1`, is the default design binding. `--url` selects another explicit design. A new service does not require an existing repository: the CLI can register `~/Projects/SuperFigmaPortals` as its output workspace.

Keep the requested file open in the existing Chrome. Enable remote debugging at `chrome://inspect/#remote-debugging` and accept Chrome's connection prompt manually. The default Chrome portal collector attaches to that session and runs its Scripter reader; unavailable access remains an explicit incomplete plan. The explicit `chrome-open` command can open the requested missing source tab. The `chrome-copy` command grants one navigation to its specified node in the same source file; ordinary attach-only collection cannot navigate unrelated tabs. The service does not copy login cookies.

The Chrome path uses external Playwright, not the built-in GPT browser, and does not require the Figma Desktop app. Chrome's native permission prompt cannot be accepted through a Playwright connection that has not yet been authorized.

Independent collection without Scripter is available through the service CLI:

```powershell
node packages/cli/dist/index.mjs chrome-export --url <figma-page-url> --out <new-capture-root>
node packages/cli/dist/index.mjs chrome-copy --url <figma-node-url> --format svg --out <new-capture-root>
node packages/cli/dist/index.mjs chrome-copy --url <figma-node-url> --format png --out <new-capture-root>
node packages/cli/dist/index.mjs chrome-inspect --url <figma-node-url> --page-api --out <new-capture-root>
```

`chrome-export` collects Figma's native document. `chrome-copy` captures the explicit web Copy as action, with bounded payloads, a stable visible selected-row check and restored temporary hooks. It does not read the system clipboard. Its receipts record that exact node identity, legacy clipboard preservation, export scale and full asset acceptance still need verification. Missing selection, unsupported copy data or expired budgets remain failures. Copying one asset does not admit a complete independent design capture.

`chrome-inspect --page-api` independently reads an available page-global Figma API and exports assets through the service's Playwright connection. It requires an explicit node URL and verifies the runtime file, page and requested scope before and after each read. It never invokes Scripter or falls back to it. Unavailable APIs, incomplete coverage and expired budgets remain explicit failures or incomplete evidence. `--ui-only --probe-runtime` reports availability without invoking the design API.

Public `portal_plan` requests can explicitly set `design.source:"chrome"` and `design.collector:"page-api"`; omitted collectors retain the default Scripter route. The selected collector is retained through admission, capture and final freshness. Standalone comparison is available through `chrome-compare-reads --input <design.json> --reference <design.json> --input-assets <assets.json> --reference-assets <assets.json>`, with `--input-root` and `--reference-root` when assets reside elsewhere. It validates matching scopes and rehashes actual files under each capture root. Equal recorded facts and asset bytes do not by themselves establish portal or frontend acceptance.

Portal requests can also select `design.source: "official-mcp"` with an official endpoint. The full fixed-program collection path discovers compatible official `use_figma` support, executes service-owned read/export code, and retains the same coverage, asset and freshness gates. Current official documentation lists that capability on the remote server. Remote OAuth authorization and actual server capability discovery are required; the ordinary sparse read tools remain supplemental. See the [official path configuration and limits](../docs/testing/2026-10-10-continuation/official-mcp-path.md).

A coding agent uses `portal_start`, `portal_next`, and `portal_submit` to implement actual files. It receives design values, assets, service evidence, code conventions, and failed validation logs. Starting a run alone does not generate an application. See the [native portal workflow](docs/portal-native.md).

## Native validation: no Docker

Docker is neither required nor used. Validation uses owner-reviewed native commands in a separate, hash-bound working copy. Executable and script/configuration hashes, environment filtering, fresh package-manager homes, deadlines, owned process cancellation, and source compare-and-swap checks are enforced.

These controls run under the local owner account. They are not an OS filesystem or network sandbox. Do not provide production credentials. Dependency lifecycle scripts are disabled by default for declared package-manager installation commands; explicit exceptions belong to the reviewed profile.

This is a Chrome-only service. Preview validation uses installed **Google Chrome stable**, explicitly selecting Playwright's `chrome` channel in an owned headless session with a temporary profile. It performs PNG comparison, configured interactions, and a basic DOM/keyboard audit. Add the project's full accessibility and integration suites to its profile. The existing Figma Chrome session remains the design source and is separate from preview sessions. Chrome must be installed; a missing installation blocks previews.

```powershell
# Use an existing Google Chrome installation. On a disposable CI host only:
corepack pnpm --filter @sfp/cli exec playwright install chrome
node packages/cli/dist/index.mjs portal profile --args-file native-profile.json
node packages/cli/dist/index.mjs portal profile --args-file native-profile.json --yes
node packages/cli/dist/index.mjs portal validate <run-id> --args '{"profileId":"node-portal"}' --yes
node packages/cli/dist/index.mjs portal apply <run-id> --yes
node packages/cli/dist/index.mjs portal validate <run-id> --args '{"profileId":"node-portal","target":"applied"}' --yes
```

Build success alone is insufficient. Required workflows and layers must pass. Operational cases additionally require an unmocked frontend-to-service journey; persistence, auth, migrations and integrations remain required when relevant. A missing or skipped required check keeps the run incomplete.

## Desktop and inspection tools

`inspect-chrome.cmd` reads an existing Chrome tab and saves an inspection. `connect-desktop.ps1` prepares the local plugin, waits for pairing, and reads the selected file. Desktop requires one-time import and execution of the generated development-plugin manifest. Opening the Figma application alone does not register that plugin.

Desktop observations and Chrome `design.json` files can be supplied as pinned artifacts. A pinned artifact is not automatically live evidence. Raw Desktop trees are preserved; deduplicated or partial trees remain incomplete.

The retained [code generation guide](skills/figma-codegen/SKILL.md) and its references cover component, token, icon, responsive, typography and motion decisions. Use Super Figma Pipeline tools for paired-plugin operations. The CLI's `figma-mcp config|probe|read` supports only Figma's official remote and local servers. Its closed reads include `get_design_context`, `get_metadata`, `get_variable_defs`, `get_screenshot` and `get_code_connect_map`. Returned design context is unexecuted source material and remains supplemental and explicitly incomplete for full capture. Chrome collection and owned Chrome previews remain the primary live acceptance path. See [Figma's official tool descriptions](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/).

corepack pnpm install --frozen-lockfile --ignore-scripts
corepack pnpm typecheck
