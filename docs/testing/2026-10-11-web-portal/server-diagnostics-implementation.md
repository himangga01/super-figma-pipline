### Implemented behavior

One node-only diagnostics implementation in `packages/mcp/src/diagnostics.ts` serves the portal, its imported public CLI and the daemon. It uses the existing direct MCP-source dependency pattern and adds no dependency or browser-side shared export. The JSONL records carry component, timestamp, process ID, level, safe event labels, route/method, phase, duration, HTTP status/outcome, request/job/workspace/run IDs when available, and hashes/counts for arguments, outputs and operation/generation identity.

The portal generates a request ID and returns it in `x-sfp-request-id`. Validated portal request/job correlation propagates through outbound CLI headers. The daemon generates its own HTTP request ID and records the portal's parent/job IDs. The CLI records the daemon's response ID. A documented process-wide `Symbol.for('sfp.diagnostics.context.v1')` asynchronous context preserves this handoff across separately built portal and CLI bundles. Correlation headers never confer authority.

Portal HTTP errors, audited operation failures, service-job preparation/state/execution/settlement failures, retained operations, daemon authorization/control/HTTP failures, normal responses and orderly readiness/shutdown events now have diagnostic coverage. Existing user activity records and operation-state rules remain independent. A response event means a response was sent. Job/operation state still determines whether execution succeeded, failed, cancelled or remained unknown.

Persisted logs are `<portal-state>/diagnostics/portal.jsonl` and `<daemon-state>/diagnostics/daemon.jsonl`. Defaults are four retained files of at most 1 MiB each and at most 128 queued events per logger. `SFP_DIAGNOSTICS_LEVEL` supports `debug`, `info`, `warn`, `error`, and `off`, defaulting to `info`. Queue pressure and write failures expose independent counters and sanitized stderr signals. `GET /api/health` exposes the portal's relative log location, logging level/limits and counters without exposing log contents or private roots. The packaged [debugging guide](../../../service/packages/portal/DEBUGGING.md) explains how to trace the already-visible job ID; it ships with the portal artifact and is linked from the service README.

Privacy uses a closed projection. Bodies, code, arguments, results, headers, cookies, nonces, arbitrary error inputs/messages, absolute paths and private browser URLs are omitted. Unknown codes/labels and operation/generation identity are hashed. Error messages retain only a hash of their first 4,096 characters and their length. Known source-catalog error codes, including known message prefixes, remain readable. Cause chains stop at four entries, detect cycles and survive throwing getters/proxies. Stack frames retain only catalog-approved module basenames and line/column numbers; source and built-entry locations remain distinguishable by their suffixes.

### Limits, risks and continuation

Diagnostics are asynchronous operational records, not a transactional journal. Abrupt termination can lose queued records. Portal close waits for pending diagnostics; daemon shutdown flushes after HTTP teardown under the existing hard-exit backstop. These shutdown waits are separate from cancellation and typed response paths. Rotation can discard earlier records and queue pressure can drop events, with observable counters/signals.

The writer rejects diagnostic directory/file links, nonregular files and multiply linked files. It uses existing owned-state protection and native filesystem handles. It does not introduce a hardened filesystem boundary equivalent to the service's atomic-file authority, an operating-system sandbox, or complete protection from same-user path replacement races. Legacy human-readable log callback semantics remain unchanged; the closed privacy guarantees above apply to the new JSONL diagnostics and its failure signals.

The closed catalog must be updated deliberately for newly introduced readable labels; otherwise new labels remain hashed. A daemon read-only diagnostics endpoint and a dedicated log viewer are not implemented. The portal health metadata and shipped guide satisfy this bounded implementation's discoverability; the owner can decide separately whether a broader public log-viewing feature is useful.
