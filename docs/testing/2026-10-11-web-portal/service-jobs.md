## Implemented boundary

- `GET /api/service/catalog` reads the actual 128 MCP tool definitions and the parent's 58 fixed CLI feature descriptors. Tool arguments use the existing Zod parser. CLI aliases retain their separate descriptor identity; the counts do not mean 186 distinct capabilities.
- `POST /api/service/jobs` accepts only `{type,name,args,workspaceId,targetSelector}`. The selector is the shared service discriminated union, including exact session or stable-file identity when selected. Unknown functions, extra approval-bypass fields, invalid arguments, unavailable workspaces and incompatible selectors reject before dispatch.
- `GET /api/service/jobs`, `GET /api/service/jobs/:id` and `POST /api/service/jobs/:id/actions` expose retained jobs and explicit approve, reject, cancel and inspect actions. Mutations retain the existing Host, Origin and CSRF guards.
- The same public `ControlClient` issues operation IDs, invokes tools, makes fixed feature calls, reads operation proof and submits approval decisions. The original ID is durably retained before invocation. The adapter always disables automatic service approval and propagates the original cancellation signal and remaining deadline.
- CLI functions requiring an owner decision first wait for a portal confirmation tied to the original parsed input hash, workspace, target and deadline. The currently active job exposes an ephemeral `requestPreview` so the owner can review those exact arguments. Confirmation does not substitute for a later service-policy approval.
- Generic jobs and guided workflows share the four-operation reservation limit. Unknown overlapping mutations fence later mutations in both entry points. Actual read-only diagnostics and closed explicit recovery operations remain available. Registry `kind:'local'` is preserved; the trusted adapter separately recognizes read-only `portal_status` and the bounded cancel/reconciliation exceptions.
- Admission is rechecked on local approval, queued execution and before/after retaining each operation. This closes the independently reproduced case where a previously pending confirmation could run after a different operation became unknown. No arguments are rewritten and no original deadline is renewed.
- A late approval or rejection response cannot overwrite a completed or unknown job. Inspection accepts only a schema-valid authenticated journal record or tombstone matching the original operation ID, kind, name and workspace with a terminal disposition. Composite/local effects cannot be declared resolved from an unrelated child operation.

## Durability and privacy

`service-jobs.json` is an atomically replaced owner-state file with at most 200 retained jobs and two MiB of metadata. It stores identifiers, validated target scope, the input hash, original operation identities, state, safe error codes and output hash/size. It stores no raw arguments, source code, result bodies, lease IDs, pairing codes, OAuth tokens or private control credentials. Older job rows are not silently deleted. Capacity or a durability failure prevents a new job from dispatching.

Actual output is available only in the current process, bounded to eight MiB per result and 32 MiB total. A hash/size remains after restart; missing raw output is displayed explicitly and is never regenerated by replaying effects. This is a deliberate persistence boundary, not a claim that the output itself survived a restart. Portal confirmations without dispatch are cancelled on restart. Other interrupted jobs remain unknown, preserving their original operation pointers.

Activity history records only the closed function type/name, job/workspace IDs, action, state and safe error code. It does not copy requests, headers, arguments, outputs or approval credentials. Necessary cancellation and inspection continue when activity persistence fails, with the established visible audit warning. The separate activity capacity/history rules remain unchanged.
