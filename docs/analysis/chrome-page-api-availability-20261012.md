## Why previous availability does not establish current availability

The historical October 11 record reports complete page-API collection around 20:06 KST and a 21:26 probe with `available:true` but `identityVerified:false`, page `1378:120`. That older probe could observe an API/page while lacking a matching runtime file key. It was already insufficient for admitted source capture. Current evidence is a different failure: the selected main page no longer exposes a usable API object to this reader, so it fails before file-key or scope ancestry validation.

`figma-page-reader.ts:171` uses `page.evaluateHandle`, reading **main-page `globalThis.figma`**. It requires `getNodeByIdAsync`, a `PAGE` current page, an independently matching runtime `fileKey`, the requested node's ancestry and stable API/page/scope object identity. It creates fresh retained handles for each read and does not restore an old API from a prior capture. It does not search plugin frames or initialize a plugin. `browser-session.ts:560` probes the same main-page property but never invokes its methods. Its safe fields distinguish absent objects/keys from readable, mismatched keys.

`observeFigmaPage` instead defines `ready` from matching file URL, application marker, visible canvas and absence of login/access-block indicators. It does **not** require Design Mode, an unobstructed menu, or page API exposure. Therefore the current `ready` observation, absent API and blocking Dev Mode dialog are consistent. Successful browser attachment is also consistent with unavailable page API.

The current evidence supports the Dev Mode dialog as the native-export obstruction. It does **not** prove that Dev Mode caused the disappearance of `globalThis.figma`, that a particular Scripter operation changed the runtime, or that returning to Design Mode will restore API exposure. Reload, editor mode, application lifecycle or a changed evaluation context remain hypotheses until a fresh guarded probe distinguishes them. Do not fill an absent file key from the requested URL, relax the identity guard, inject another collector's API/facts, or relabel plugin-frame reads as independent page-API acquisition.

## Independent collection fallback and admission limits

The existing public **`chrome.export`** path uses Figma's own File / Save local copy UI, captures the actual `.fig` Blob before revocation, verifies byte bounds/magic, saves it atomically, and records its digest. It does not require `globalThis.figma` or Scripter. Existing **`chrome.decode`** decodes native nodes/styles/images and selects the requested scope from the exported document; **`chrome.copy.svg`** and **`chrome.copy.png`** provide separately requested UI asset actions. These are supported independent building blocks, provided the coordinator observes the workspace fence and obtains new explicit authorization rather than replaying a failed capture.

Raw native export truthfully returns `fullCapture:false`. Export/decoding alone does not establish complete source facts, current page/scope binding, SVG/root-PNG oracles, original-image parity, unknown-field completeness, freshness or frontend acceptance. Current portal Chrome collector admission supports `page-api` and `scripter`, not a native-export collector. A complete native-export fallback would require a distinct provenance/admission adapter, verified scope/fact/asset normalization and independent fresh export proof. It must not be labeled page API, seeded from Scripter output or admitted by changing comparison thresholds. That broader adapter is outside the immediate modal repair.
