## Current architecture and public recovery behavior

`service/packages/cli/src/service-functions.ts:64-80` defaults public CLI descriptors to composite execution proof. Chrome inspection, export and copy are write-classified because they can write local capture outputs and perform source UI actions (`:271-322`). `service/packages/portal/src/control.ts:128-142` permits genuinely read-only and selected recovery functions while preserving write classification for those captures. Daemon invocations are retained through `beforeInvoke` before dispatch (`:155-169`), but a CLI-local Chrome path does not issue such a daemon operation.

`service/packages/portal/src/service-jobs.ts:417-428` marks execution started before calling the runtime. On exception, a non-read-only executed composite becomes unknown even with zero daemon operations (`:520-525`). This is conservative and consistent with partial local capture: zero daemon journal rows does not mean zero filesystem or browser effects. It also treats the connection-only failure as unknown because no stronger local proof exists.

The public actions are approve, reject, cancel and inspect. Inspect is advertised for every unknown job (`:223-225`), but `action(..., inspect)` immediately returns unchanged unless proof is single-operation and there is exactly one retained operation (`:567-570`). Only an authenticated, exact original daemon record/tombstone with matching identity, workspace and terminal disposition can settle that supported case. Cancel requires a still-active execution (`:601-605`); completed unknown jobs have no active entry. Restart preserves unknown rows and converts other dispatched pending states to unknown. There is no expiry-based clearing, local abandonment action or public job deletion.

`hasUnknownMutation` (`:264-269`) blocks non-read-only, non-recovery requests if an unknown write belongs to the same workspace, either job/request scope is null, or the old unknown is null-scoped. Consequently, one workspace-specific capture unknown also blocks ordinary null-scope administration through the public function surface. It does not block every other named workspace. `PortalBridge.start` (`service/packages/portal/src/bridge.ts:283-290`) uses the same predicate before starting a workflow. Pending approvals are checked again at execution/approval boundaries, so an earlier approved request cannot legitimately bypass a newly established fence.

The public `operations.resolve` and `operations.cancel` features remain reachable as recovery paths. They address an original daemon operation ID, not a portal job UUID. `service/packages/mcp/src/control/operation-endpoints.ts:143-155` requires an existing authenticated `outcome-unknown` journal record for resolution. Fabricating a daemon ID for a zero-operation local capture cannot satisfy that contract. Workflow inspect/reconciliation operates on its own retained run/original daemon operation and cannot settle a separate service-job composite. Public job Inspect therefore produces a misleadingly actionable no-op in these cases.

The direct workspace-registration route exists separately from the job fence, and a different existing workspace can also be eligible for different work. Neither is recovery of these unknowns. Creating a nominal new workspace, using CLI directly, copying a state root or relabeling a write as read would evade the overlapping-work protection and is not a recommended continuation. The current portal effectively fences these attempts indefinitely; a future genuine implementation change is required to provide honest local recovery.

## Minimal owner-controlled recovery proposal

Keep **job outcome** and **owner disposition of its fence** separate. Do not use `failed`, `resolved-not-applied` or success for old jobs based on a message, empty operations, missing folder or elapsed deadline. Proposed initial scope is a closed allowlist of local Chrome capture capabilities with zero daemon operations and a non-null, still-valid workspace. Broader composites, null-scoped jobs, journal-backed operations and guided-run uncertainty retain their existing recovery rules.

Add a public action such as **Abandon this local attempt and acknowledge its unresolved outcome**. It must never call the original feature, reconstruct arguments or replay an operation. The owner reviews the exact job, original deadline, error, known partial evidence, workspace and explicit warning that unknown effects remain unknown. The action records a separate durable disposition, for example `fenceDisposition:"owner-abandoned"`, with job/row fingerprint, workspace identity, confirmation timestamp, reason/evidence hashes and actor `local-owner`. Job status, creation/deadline, arguments hash, original error, output metadata and evidence remain unchanged. The UI must continue to display Unknown and show who acknowledged continuation risk. Only that specific acknowledged row stops contributing to the mutation fence; other unknown rows still block.

Bind confirmation to a server-issued short-lived, one-use challenge containing the exact row fingerprint/revision and workspace identity. Use existing same-origin/CSRF and durable audit conventions, and reject stale confirmations, concurrent row changes, different scope, repeated challenge use or unavailable workspace. The confirmation window is new decision authority, not a renewal of the original execution deadline. Log only sanitized identifiers and hashes, never confirmation material or private evidence contents. A durable-write failure leaves the fence active; an ambiguous response requires readback of the disposition, not automatic repeated mutation.

Require producer quiescence before enabling this action. `active` being absent is insufficient: the current job races execution with cancellation and releases its active slot in finally, while the underlying promise or retained Chrome transport can still exist. Track the underlying runtime promise and any source-changing intent/cleanup completion, not only the caller-facing promise. If a pending open/select/navigation/export action or unconfirmed cleanup can still complete, report **recovery blocked: execution cleanup unconfirmed**. Do not assume a stopped timer cancelled an issued click. A read-only browser-attachment handshake with no source-changing intent can be treated separately, but that distinction needs trusted runtime evidence. Historical/restarted rows without such evidence require an explicitly established producer-retirement/cleanup boundary plus the owner's risk acknowledgment; they must not be automatically declared quiescent from an old error code. This is a concrete implementation prerequisite, not an instruction to restart anything now.

After acknowledgment, any continuation is a **new explicitly reviewed request**, with a new job/capture-attempt identity and fresh output directory. Recovery itself dispatches nothing and offers no Replay button. Normal target, workspace, egress, approval and deadline checks still apply. Do not copy an old grant or renew an old run. The existing workflows and original unknown jobs remain available for inspection. An acknowledgment does not accept their output or settle their daemon evidence.

A smaller first UI repair can accurately disable no-op Inspect with the reason **This local composite has no daemon-operation proof; owner recovery is not implemented** and list the affected fences. That improves honesty but does not restore usability. A narrow durable owner disposition is the minimum functional recovery; a generic composite transaction/resume system is unnecessary for this initial scope.

## Prospective trusted pre-effect proof

Separately prevent avoidable future fences when the runtime can prove failure before capture effects. Use a private runtime-owned phase tracker or unforgeable receipt, bound to the exact job/feature invocation. Do not recognize a caller `code`, `message`, `emit` payload, prototype or claimed phase as proof. Mark the effect boundary **before** capture-folder creation/write, source-tab creation/navigation/selection, Dev Mode dismissal, menu/export/copy action, daemon invocation or publication of a deferred source-changing transport intent. Connection/session initialization itself can include focus emulation and deferred open/select intents; it is not automatically a pure read.

Only a trusted terminal failure with no boundary crossed, no retained invocation, no deferred mutation intent and confirmed producer settlement can become a normal failed/cancelled new job. Portal job/audit/diagnostic metadata persistence is expected bookkeeping and must be distinguished from capture/output/source effects. Persist the safe proof with the terminal row so restart does not infer a missing phase as proof. If persistence or cleanup is unconfirmed, retain unknown. A fully completed rotation or a typed connection error is unrelated to this execution-proof contract.

This mechanism is prospective. It must not migrate the three old jobs to failed by reading their error codes or examining current directories. The current 180-second failure can guide a new regression case, but it is not an existing public proof accepted by the frozen 31e4 store.

Update the job-detail region without resetting unsent feature inputs, selection or approvals. Coalesce/limit progress updates, do not persist one row per polling tick, and drop late progress after terminal settlement. Show stage and original timeout honestly; do not invent percentage completion or reset the clock. Progress failure must not turn an execution into success or block cancellation.
