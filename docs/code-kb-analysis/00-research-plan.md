## 조사 절차

1. `.git` 내부와 설치·빌드 산출물을 제외한 모든 로컬 파일 경로를 고정한다.
2. 각 파일의 크기, 줄 수, 확장자, 역할 분류를 인벤토리에 기록한다.
3. 진입점부터 호출 그래프를 따라가며 프로토콜, 도구 등록, Figma 플러그인 핸들러, 전송 계층, 데이터 모델, 오류 처리, 보안 경계, 테스트를 분석한다.
4. 선언된 기능은 README가 아니라 구현 파일과 테스트에서 교차 확인한다.
5. 의존성·빌드·배포·라이선스·유지보수성·확장성을 프로젝트별 동일 기준으로 평가한다.
6. 동일 모델과 추론 수준을 상속한 서브에이전트 3명이 각각 1차 분석을 작성한다.
7. 각 개별 보고서마다 나머지 2명이 누락·과장·오류를 검토하고, 원 작성자가 근거를 재확인해 수정한다.
8. 비교표와 통합 제안은 3명이 독립 점수·권고안을 낸 뒤 반론과 합의 라운드를 수행하고 메인 에이전트가 최종 편집한다.

## 전수조사 판정 기준

- 인벤토리의 파일 수가 같은 제외 규칙으로 다시 계산한 `rg --files --hidden -g '!.git/**'` 결과와 일치해야 한다.
- 모든 파일은 최소한 한 개의 역할 분류를 가져야 한다.
- 핵심 기능 주장은 구현 경로 또는 테스트 경로를 함께 제시해야 한다.
- 보고서에 사용한 정량 수치는 계산 명령과 재검산 결과가 일치해야 한다.
- 원본 3개 프로젝트에는 어떠한 수정도 하지 않는다.

## 통합 서비스 설계의 준수 경계

공식 REST API와 공식 Dev Mode MCP의 호출량·좌석 비용을 사용하지 않는 **로컬 Plugin API 브리지**를 최우선 기술 경로로 평가한다. 세 프로젝트가 실제로 채택한 개발용 플러그인 사이드로드, 로컬 MCP/HTTP/WebSocket, 사용자 소유 코드베이스 처리를 기능별로 분석하고 Starter 플랜·Figma Design·데스크탑 환경에서 가능한 범위를 구체화한다.

다만 통합안은 타인의 문서 접근, 인증·편집 권한 탈취, 결제·접근통제 파훼, 역공학 또는 약관 위반 은폐를 제안하지 않는다. 사용자가 정상적으로 접근하고 편집할 수 있는 Figma 문서와 공개된 Plugin/API 표면, 명시적 로컬 플러그인 실행, 사용자 승인 작업만을 전제로 한다. 기술적 비용 회피 가능성과 공개 배포·웹 지원·Community 심사 리스크는 별도 축으로 평가하며, Figma 약관과 각 오픈소스 라이선스 검토를 배포 게이트로 둔다.
