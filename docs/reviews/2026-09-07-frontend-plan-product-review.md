# 프론트엔드 네 가지 사용 사례 계획 — 제품/요구사항 리뷰

검토일: 2026-09-07. 대상: `docs/plans/2026-09-07-frontend-four-cases-plan-ko.md` 초안 v0.1. 범위는 제품 요구·입력·완료 기준이며, 최종 채택 판단은 메인 에이전트에게 넘긴다. 초안·프로덕션 코드·기존 staged 변경은 수정하지 않았고, 브라우저/앱을 제어하지 않았다. 아래 행 번호는 검토한 v0.1 기준이다.

## 판단

**C1을 C3/C4의 상위 진입점으로 두는 것은 요구사항을 훼손하지 않는다.** C1은 사용자가 Figma로 신규 프론트엔드를 요청하는 방식이고, C3/C4는 reference 활용 여부에 따른 실행 전략이다. 요청한 경우와 실행 전략을 모두 기록하고 네 경우를 각각 인수 테스트하므로 사용자 경험을 없애는 통합이 아니다. 명시적 C3를 C4로 바꾸거나 C4에서 주변 저장소를 참조하지 않는 규칙도 적절하다(계획 21–26, 66, 152–156행).

**신규 서비스에서 기존 저장소가 없어도 진행하는 정책은 충족한다.** 경로 자동 할당, stack 선택의 선택성, URL binding 재사용이 명시되어 있다(15, 26–28, 131행). 다만 이 약속을 요청 스키마와 CLI까지 일관되게 적용하는 인수조건을 PRD-05에서 보강하도록 권고한다.

프론트엔드 범위, 기존 API 보존, reference 읽기 전용, 관측과 가정의 구분은 적절하다. **P0 이슈는 발견하지 않았다.** 구현계획 확정 전에는 P1 세 건을 보완할 것을 권고한다. 주된 위험은 네 경우 중 하나가 누락된 것이 아니라, 화면 범위나 UX가 일부 빠져도 성공으로 해석될 여지가 남아 있다는 점이다.

## PRD-01 — 화면 범위 생략의 기본값과 누락 방지 기준

**근거:** 계획 49·58행은 화면 범위/`pageScope`를 입력으로 요구하지만 122–125행 CLI에는 범위를 지정하는 방법도, 생략 시 규칙도 없다. 이미 알려진 초기 node는 `0:1`이며(11행), 160행은 Home/Shop/Single Product/Cart/Checkout “등 실제 확인된 scope”를 사용한다고만 한다. 기존 수집기는 미완료 범위를 `pendingScopes`, `truncated`, `coverage`로 별도 보존한다(`service/packages/cli/src/snapshot-reader.ts:248`, `:253`, `:256`). 이 값은 구현할 화면 목록 자체가 아니다.

**문제:** Figma URL만 준 C1/C4에서 에이전트마다 Home만 선택하거나 여러 화면을 선택할 수 있다. 부분 수집에서 보이는 화면만으로 범위를 확정하면 읽지 못한 화면이 구현 범위에서 사라진다. 반대로 문서 root에 있는 UI kit·설명판까지 전부 route로 만들 위험도 있다. 이 상태에서는 동일 Figma로 네 전략을 비교한다는 인수조건의 분모가 고정되지 않는다.

**개선안:** `pageScope`의 원시 요청과 해석된 범위를 구분한다. 생략 시 저장된 binding의 node를 시작점으로 화면 후보·반응형 변형·컴포넌트 자료를 분류하여 `included`, `excluded(reason)`, `unresolved(reason)` 목록을 만든다. 파일·화면 이름을 미리 확정된 관측값으로 취급하지 않는다. 일반적인 판단은 근거와 가정을 표시하고 진행하되, 수집 미완료 범위를 누락으로 숨기지 않는다. route별 필수 section·상태와 미관측 추론을 blueprint에 연결한다.

**인수조건:**

- 저장된 Figma binding만 있는 C1 요청이 URL·기존 저장소·stack 재질문 없이 화면 목록과 신규 경로를 포함한 계획을 생성한다.
- 같은 캡처를 사용하는 C1/C2/C3/C4 fixture는 동일한 화면 범위 ID를 사용한다. 레거시 제약으로 실현하지 못하는 항목은 제거하지 않고 차이로 남긴다.
- UI kit와 중복 responsive frame은 사유가 있는 자료/변형으로 분류되고 독립 route로 오인되지 않는다.
- `pendingScopes`가 남으면 미해결 범위가 유지된다. 재수집 시 새로 발견된 화면을 단순히 범위 밖으로 처리하지 않는다.

## PRD-02 — 완료 판정에 필수 범위와 필수 검사 조건을 연결

**근거:** 계획 63행은 `skipped/blocked`를 보고서에 넣고, 64행은 성공을 실제 파일 hash에 연결하며, 109행은 누락을 scope에 남긴다. 114행은 Chromium 실검증이 없어도 미수행으로 표시한다. 그러나 어떤 미수행/누락이 있으면 전체 완료가 불가능한지는 정의하지 않는다. 기존 `InspectionV1`도 values/assets의 `captured|partial|unavailable`을 구별한다(`service/packages/ir/src/inspection-v1.ts:29`). 수집 CLI의 상위 `status: 'captured'`에는 `truncated`가 동반될 수 있으므로 상위 상태만으로 완전성을 판단할 수 없다(`service/packages/cli/src/commands.ts:314`, `:337`).

**문제:** 실제 파일 hash와 성공한 build가 존재하고 나머지 검증이 `skipped`여도 “신규 프론트엔드 완료”로 표시할 수 있는 해석이 남는다. 필수 화면 일부, 이미지, 키보드 동작이 빠진 결과와 합의된 범위를 구현한 결과를 사용자가 구별하기 어렵다.

**개선안:** 계획 단계에서 필수 route/section/state와 필수 check를 고정하고, 결과에 구현 범위 완성도·검증 결과·디자인 근거 상태를 별도로 둔다. 전체 완료는 필수 구현의 충족 및 필수 검사 통과에 연결한다. 필수 검사의 `skipped/blocked`는 통과로 계산하지 않는다. 비필수 브라우저 검증과 계획 단계에 명시한 demo 한계는 별도로 표시한다. 캐시 사용 자체로 모든 작업을 차단할 필요는 없지만, 캐시 기준 구현 완료와 최신 Figma 실측 검증 완료는 구별해야 한다.

**인수조건:**

- build/typecheck가 통과해도 필수 route 누락 또는 필수 interaction 검사 미수행이면 전체 완료가 아니다.
- 필요한 이미지/폰트 누락, 부분 수집, `waiting-agent`, 예산 소진에 대해 사용자가 볼 결과 상태와 다음 행동이 각각 정의된다.
- 필수/비필수 검사와 허용된 차이는 실행 전에 기록된다. 실패 후 필수 항목을 제거해 성공으로 만들지 않는다.
- 미지원 Chromium만 비필수로 제외한 실행은 그 한계를 명시한 채 완료될 수 있고, 모든 browser 검사가 미수행인 실행은 UX 검증 완료로 표시되지 않는다.
- 캐시로 만든 파일의 검증이 성공해도 “현재 Figma와 일치 검증됨”으로 표시하지 않는다.

## PRD-03 — 레거시 관례 우선이 Figma UX의 조용한 축소로 이어지지 않도록 명시

**근거:** 계획 72행은 C2에서 API/구조·package 관례를 Figma 시각·상호작용 요구보다 우선하고 충돌 시 최소 변경을 명시한다. 154행의 C2 인수증거는 재사용·package·사용자 변경 보존·회귀에 집중한다. 현재 분석 결과는 component/token/icon 후보와 재사용 guidance를 제공하지만 UX 보존을 보증하지 않는다(`service/packages/cli/src/project-inspector.ts:101`, `:121`).

**문제:** 기존 공용 컴포넌트가 Figma의 필수 상태·키보드 동작·drawer 패턴을 지원하지 않을 때, 기존 관례를 유지했다는 이유로 그 요구를 생략해도 되는지 불명확하다. 기존 UI의 회귀 검사가 통과하는 것과 요청한 Figma UX가 통합된 것은 다른 인수조건이다. 또한 의도한 디자인 변경까지 “baseline 대비 회귀”로 해석하면 개선 작업을 막을 수 있다.

**개선안:** 실제 API 계약·업무 규칙의 보존과 frontend 구현 관례를 구별한다. 관례 충돌은 재사용, adapter/variant 확장, 새 frontend 컴포넌트 중 최소 변경으로 해결하되 Figma 필수 UX는 유지한다. 실제 계약 때문에 불가능한 항목은 관측한 API 제한·영향 화면·대안을 기록하고 해당 UX를 미완료로 남긴다. baseline 검증에는 의도한 변경과 유지해야 할 기존 동작을 나누어 기록한다.

**인수조건:**

- 기존 컴포넌트에 필요한 상태가 없는 C2 fixture에서 기존 API를 보존하면서 frontend variant/adapter로 필수 UX를 구현한다. 관례를 이유로 상태를 삭제하지 않는다.
- API가 지원하지 않는 Figma 행동은 성공한 것처럼 보이게 하지 않고 제한과 대안을 결과에 남긴다.
- C2에도 Figma route/section/state 충족 검사가 적용된다. 재사용 횟수나 기존 테스트 통과만으로 합격하지 않는다.
- 의도한 디자인 변경은 예상 차이로 기록하고, 영향 없는 기존 route와 API 계약의 회귀는 별도로 검사한다.

## PRD-04 — backend 없는 기능의 런타임 표현을 인수조건으로 고정

**근거:** 계획 12–13행은 frontend-only와 가짜 로그인/결제 성공 금지를 정하고, 112행은 fixture/adapter와 README의 demo 표시를 제시한다. `FrontendBlueprintV1`에는 interaction/state가 있으나 외부 서비스 의존 행동의 모드·최종 표시 규칙은 없다(61행).

**문제:** 원칙은 적절하지만, README만 읽지 않은 실행 화면 사용자에게 제출 버튼이 무엇을 하는지 일관되게 전달할 기준이 없다. 아무 반응 없는 버튼이나 끝나지 않는 loading도 가짜 성공은 아니지만 UX 완성으로 보기 어렵다.

**개선안:** interaction별로 로컬 동작, fixture 시뮬레이션, 기존 API 연결, 현재 미지원 상태를 분류하고 최종 화면 문구·오류·loading 해제 조건을 blueprint에 기록한다. demo 제한은 관련 화면에도 표시한다. 이 구분은 신규 backend를 추가하는 이유가 되어서는 안 된다.

**인수조건:** C1/C3/C4의 cart/quantity/filter는 로컬 데이터로 실제 동작한다. Checkout은 입력 검증 후 “데모이며 주문이 접수되지 않았다”는 명확한 상태에 도달하고 실제 주문/결제 요청은 하지 않는다. 로그인 fixture는 인증된 것처럼 표시하지 않는다. 지원되지 않는 동작은 설명과 함께 표시되며 무응답/무한 loading으로 남지 않는다.

## PRD-05 — C1 신규 입력의 생략과 reference 선택을 모든 진입점에서 동일하게 처리

**근거:** 계획 21·26·28행은 C1의 reference 선택성과 새 경로 기본값을 정하지만, 58행의 strict request에는 `target`과 `pageScope`가 필드로 나열되어 생략·정규화 시점이 없다. 122행의 `--case new`에는 선택적 `--reference`가 없는데 153행 인수조건은 “C1 신규, reference 제공”을 요구한다. 현재 inspector는 실제 기존 root를 `realpath()`하는 분석기이므로 신규 요청을 그대로 이 경로에 연결하면 안 된다(`service/packages/cli/src/project-inspector.ts:83`, `:92`).

**개선안:** 원시 사용자 요청 → 기본값/저장된 binding 해석 → strict 실행 요청의 순서를 명시한다. C1의 CLI/API 양쪽에 선택적 reference를 노출하고, 신규 경로가 해석되기 전에는 기존 저장소 존재를 요구하는 분석기로 보내지 않는다. 새 출력 경로가 자동 할당되었음을 표시하되 이미 허용된 신규 생성에 일괄적인 추가 확인 단계를 넣지 않는다.

**인수조건:**

- `--case new`와 저장된 binding만으로 `blank-new` 계획이 생성된다. 기존 target·reference·stack은 필수가 아니다.
- `--case new --reference <repo>`는 `requestedCase=C1`, `resolvedStrategy=reference-new`를 보존한다.
- 명시적 C3에 reference가 없으면 빠진 reference만 요청하고, 저장된 Figma URL을 다시 묻거나 C4로 전환하지 않는다.
- 명시적 C4는 주변에 분석 가능한 repository가 있어도 reference 읽기를 하지 않는다.

## 검토 제한과 메인에게 넘기는 판단

이 문서는 정적 계획 리뷰다. 기능 동작·브라우저 접근·실제 Figma scope의 최신성을 검증했다고 주장하지 않는다. 기존 수집/분석 소스의 필요한 부분만 확인했고 실행 테스트는 수행하지 않았다. P1 세 건의 반영을 권고하되, 네 사용자 경우를 네 개의 별도 실행 엔진으로 나누라는 제안은 아니다. C1 상위 흐름과 신규 경로 자동 할당 정책은 유지하는 것이 적절하다.
