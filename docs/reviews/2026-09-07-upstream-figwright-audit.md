# Figwright upstream feature utilization audit

Date: 2026-09-07. Scope: static audit of the original Figwright feature surface and its use in the current service. This report does not modify the plan, production code, upstream checkout, existing staging, or historical reviews. No browser was operated and no tests were rerun for this audit.

## Conclusion

**The service retains all 112 original Figwright tool names, but the evidence does not support saying that every original capability is fully used by the portal workflow.** All 112 have a manifest row, a registry symbol, an implementation file and an existing declared test path. Both product skills and all ten supporting references are present. However, the Chrome inspection and grounding-graph paths use only part of the original mapping behavior; Desktop connection stops before complete asset extraction; the skills retain instructions that conflict with the current product rules; and the portal generation/application/runtime workflow is still proposed work.

The corrected product scope applies here: **C4 is frontend-only; C2 and C3 must learn the complete relevant legacy/reference code and implement the UI, backend, API, data and authentication layers required for the portal to run.** Figwright's original component/token/profile analyzers are useful inputs to that work, but they are not a complete backend or application-contract analyzer. That missing orchestration is an integration gap, not an original Figwright backend feature that was dropped.

This audit separates four claims:

1. **Present:** a feature has a current registration/file/entry point.
2. **Behavior retained or replaced:** its important semantics can be followed into current implementation and tests; name equality alone is insufficient.
3. **Used in the flow:** an inspected current caller actually invokes it, or it remains an optional skill-guided path. Instruction text alone is not an executed workflow.
4. **Experimentally evidenced:** an existing result identifies a real execution and its limits. A declared test path is not a new test pass or a live Figma exercise.

## Concrete findings and next steps

### FW-01 — P1: mapping behavior is only partially used outside the canonical mapping tools

The canonical `component_map` reads `docs/figma-component-map.md`, validates recorded targets, applies overrides and reports stale overrides (`service/packages/mcp/src/tools/component-map.ts:19`, `:75`, `:119`). The canonical `token_map` reads token overrides and combines variable tokens with single-color paint-style pseudo-tokens (`service/packages/mcp/src/tools/token-map.ts:16`, `:142`, `:158`). These original capabilities remain implemented.

By contrast, Chrome inspection calls `inspectProject()`, whose direct `joinComponents`/`joinTokens` calls pass thresholds and profile options without those override inputs, and supply only variable definitions to the token join (`service/packages/cli/src/project-inspector.ts:94`, `:101`). It does not join shared paint-style pseudo-tokens. Its `mappingNodes` projection is deliberately small (`:71`); it is not equivalent to the original full design context. The Desktop reader does call the canonical component/token/icon tools (`service/packages/cli/src/desktop-reader.ts:70`), so this is a path-specific discrepancy, not a claim that every connector loses mapping support.

The grounding graph also calls the joins without recorded overrides, and constructs Figma token join inputs with `value: null` (`service/packages/mcp/src/snapshot/build-grounding-graph.ts:102`, `:175`). Its token edges consequently do not establish the original value/mode/style matching behavior. Candidate edges are honestly marked as candidates; that does not make the omitted matching evidence available.

**Next step:** extract shared mapping preparation that includes verified overrides, stale-target handling, styles, code syntax, resolved values and theme axes; use it from canonical tools, Chrome inspection and graph building. Preserve incomplete scan evidence. For C2/C3, record provenance separately for each relevant source repository and layer.

**Acceptance:** identical design/repository fixtures produce equivalent confirmed mapping decisions through Desktop, Chrome and graph paths; explicit overrides win consistently; stale rows degrade consistently; a style-only Figma palette and equal-value/different-name tokens remain matchable. No graph candidate is promoted merely because an analysis step ran.

### FW-02 — P1: retained skills are not yet adapted to the service's actual contracts

All two product skills plus ten references are byte-identical to the pinned originals. This proves retention, but also preserves incompatible instructions:

- `service/skills/figma-codegen/references/verify.md:19` and `service/packages/mcp/src/prompts/figma-to-code.ts:38` direct agents to launch Chrome headless, conflicting with the existing-Chrome restriction.
- `service/skills/figma-codegen/SKILL.md` still describes `.figwright/snapshots/`; the implemented `design_diff` stores file/node-bound baselines under `.sfp/design-diff-baselines/v1/` (`service/packages/mcp/src/tools/design-diff.ts:19`, `:48`).
- The codegen skill tells agents to use a name-matched color token despite value drift and flag it. That must be reconciled with preserving the requested Figma UX through a scoped token/variant instead of silently changing its appearance.
- Its existing-project assumptions and final rule against writing config files do not supply a runnable C4 scaffold; they also do not define the corrected all-required-layers C2/C3 workflow.

**Next step:** adapt both skills, all applicable references and both MCP prompt twins together. Keep the original asset, typography, layout, component API, theme and motion fidelity rules. Add the exact current tool cycle and per-case scope; do not spread a blanket frontend-only rule into C2/C3. Update baseline storage and approved preview instructions.

**Acceptance:** a static contract check rejects obsolete Chrome-launch and baseline-path instructions; one supported agent completes a C4 scaffold and a C2/C3 portal workflow with its required server/data/auth contracts. Changes to prompts and skill references are reviewed together.

### FW-03 — P1: collection/analysis stops before complete portal implementation

The current CLI routes `connect`, `chrome-inspect`, generic tool calls, snapshot capture and grounding refresh (`service/packages/cli/src/commands.ts:55`, `service/packages/cli/src/admin-commands.ts:233`). `inspectProject()` returns profile/maps and guidance (`service/packages/cli/src/project-inspector.ts:113`); it does not generate, apply or run an application. At audit time, `service/packages/mcp/src/frontend/`, `service/packages/cli/src/frontend/` and `service/packages/shared/src/frontend-build.ts` do not exist.

Original Figwright itself is provider-first: its tools and prompts guide an external coding agent. Retaining those capabilities does not instantiate that agent's portal generation, dependency installation, execution, repair or acceptance loop. For corrected C2/C3, UI component scanning also does not establish API semantics, database/migration requirements, authorization behavior or backend dependencies.

**Next step:** implement the proposed durable agent/application workflow and case-specific analysis. Inspect complete relevant C2/C3 source and trace each required portal behavior across UI, API, server, data and authentication before selecting changes. Use the original Figwright capabilities where they are relevant; do not call unrelated destructive canvas tools merely to increase a utilization count.

**Acceptance:** C2/C3 deliver a runnable portal with the required cross-layer behaviors and their evidence; C4 remains an independent frontend. A guidance response, scan result, compiled pipeline or `tools/list` cannot satisfy application completion.

### FW-04 — P1: Desktop entry-point capture and asset/motion use remain partial

`readDesktopDesign()` collects document/metadata/styles/variables and optional canonical code maps, but it does not execute the asset export chain (`service/packages/cli/src/desktop-reader.ts:42`). `connect` accurately labels its result `values: partial`, `assets: unavailable`, with explicit follow-up issue codes (`service/packages/cli/src/commands.ts:175`). `service/scripts/desktop-acceptance.mjs` invokes this connection command, so its name does not mean all original grounding/asset workflows are accepted.

Chrome capture does export root PNGs, deduplicated image hashes and vector SVGs, but leaves work pending beyond 64 items or 64 MB (`service/packages/cli/src/capture-assets.ts:30`, `:59`). It does not itself execute the skill's curated-icon-first selection, composited-filter fallback, empty-instance/main-component fallback, final import integration or rendered-asset comparison. Raw reactions and text segments are collected by `read-program.ts`, but the CLI does not perform a conditional full `get_node_motion`/motion-to-code sequence.

**Next step:** connect partial collection to resumable per-scope grounding and asset extraction, and conditionally retrieve component APIs, annotations, reactions and full motion where the selected design uses them. Apply the original `assets-and-icons.md` choices during generation; retain export caps as explicit remaining work rather than lowering completion scope.

**Acceptance:** a design with more than 64 assets, filtered image fills, off-canvas instances, rich text and animation either completes the required follow-up work or reports the exact unresolved items. Desktop connection alone never marks those workflows complete.

### FW-05 — P2: the manifest is not a complete non-tool utilization ledger

`service/capabilities/union-manifest.json` inventories canonical tools and source surfaces for lexical tools, Figmosha helpers and CLI parsers. It has no equivalent Figwright ledger for the two skills, ten references, two prompts, serializer fidelity, verified-map feedback, relay reliability, plugin UI or upstream development-tooling dispositions. `vendor-map.json` and `upstream-lock.json` establish provenance and ownership, not workflow usage.

**Next step:** add a versioned feature ledger with source commit/path, current implementation, behavior changes, caller/workflow, test scenario and historical/live receipt. Keep availability, usage and proof independent. Mark reverse design authoring and PDF/video export as available/conditional when portal generation does not need them.

**Acceptance:** every row below has an explicit retained/replaced/conditional/deferred/excluded disposition and verifiable evidence; no tool count is reused as a count of complete portal behaviors.

### FW-06 — P1: historical validation does not prove full original behavior or current portal use

The historical full suite records 300 files, 3,325 passes, 17 skips and zero failures, with source hash `sha256:1636f158c83838868bf1db44b3c0f21cd124c2bbc87b6890b378011ee05e0d02`. Its receipt explicitly sets `realFigmaValidated`, `targetServiceValidated` and `remoteCiValidated` to false. The isolated runtime log proves MCP wire enumeration of 116 tools, standalone package installation and daemon lifecycle, not live execution of all tools.

**Next step:** retain those receipts as historical evidence and create a case/feature scenario matrix for subsequent implementation. Bind generated-app and live Figma results to the exact source/design/artifact hashes, distinguish skipped and unsupported features, and include the corrected C2/C3 backend/API/data/auth behavior.

**Acceptance:** reports can identify which original behaviors were exercised and where, without claiming full coverage from name registration or the aggregate pass count. No rerun or new live result is claimed in this audit.

## Intentional upstream tooling exclusions and ownership changes

`service/vendor-rules.json` distinguishes copied source, merged dependency manifests, reference-only toolchain files and service-owned exclusions. The historical lock records **316 copy, two merged-manifest and 19 reference-only entries**. An exclusion in this file often means that the service now owns an adapted implementation; it must not be counted automatically as a missing feature.

The original repository's developer workflow is not required wholesale for product parity. The following are intentionally outside the copied product roots or replaced by the service workflow: `.claude` formatting hook/settings; its internal `figma-typings-audit` and `mcp-sdk-audit` skills/probe; `.vscode` preferences; `.mcp.json`; `.cspell.json`; upstream `AGENTS.md`/`CLAUDE.md`; repository contribution/security/changelog metadata; `glama.json`; `renovate.json`; GitHub issue/PR templates, branding assets and original release/CI workflows; `scripts/release.mjs` and `scripts/sync-skills.mjs`; the `skills/README.md` index. The two internal audit skills are distinct from the **two product skills** counted above.

Original `clean`, `postinstall` and `release` package scripts are explicitly excluded when merging (`service/scripts/vendor-upstreams.mjs:48`). Lockfile/workspace/TypeScript/Vitest/bundler/plugin-manifest settings are reference-only or service-owned. The original license and third-party notices must remain represented by the service's licensing/artifact process; not copying the original release script does not justify dropping attribution. No demand is made to execute or restore these upstream developer tools during portal generation.
