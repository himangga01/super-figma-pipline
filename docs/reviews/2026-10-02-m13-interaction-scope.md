## Owner input and authority

The public `portal_plan` arguments accept an optional strict `interactionScope` object. It has `version: 1`, the exact `captureFingerprint`, and `exclusions`. Each exclusion names an `interactionId`, its exact `sourceHash`, and a trimmed, nonempty owner reason of at most 2,048 characters. At most 4,096 distinct IDs are admitted. A changed capture, changed reaction hash, unknown ID or duplicate exclusion is rejected. A node bound directly to a declared required workflow cannot be excluded, even if the owner's wording contains no inferred workflow keyword.

An owner selection changes required relevance; it does not rewrite source capture. The interaction contract retains all excluded action evidence, the original unsupported reason, and the owner's separate `exclusionReason`. Required actions remain in `interactions`; exclusions remain visible in `excludedInteractions`. The bounded selection hash changes the contract and observation scope identity. The current complete-capture guard remains mandatory; exclusions do not admit partial capture, empty-action reactions or unsupported required behavior.

Workflow admission retains every raw scope and evidence row. Only an otherwise unclassified scope on an exact unique node may become covered through this selection, and only when that node has retained excluded actions and no remaining required action. Candidate requirement evidence, required source decisions and ambiguity issues retain their original obligations. A mixed required/excluded node remains unresolved until its required workflow is admitted; selection alone cannot erase it.

## Binding through implementation and validation

- Core lifecycle independently rederives the contract from the admitted capture, owner request and workflow coverage. The input context, signed preparation input and every one of the seven core manifests bind `interactionContractHash` and `interactionSelectionHash`. Signed readback verifies those bindings against the context and manifest.
- The bundle input hash includes the selection binding. The core contract adds the `evidence-bound-incidental-exclusions-v1` selection codec and preserves the existing `core-derivation-qualified-source-v3` algorithm identity. Historical optional fields remain readable; old contract hashes cannot authorize current execution.
- Derived interaction rows retain their complete raw observation. An excluded expectation contains the exact action ID, reaction source hash, selection hash and owner reason, and creates a visible `review-incidental-interaction` obligation. Required unsupported actions and incomplete capability evidence continue to produce blocking issues.
- Preview preparation consumes required assertions only, while its contract hash and scope hash retain the reviewed selection. Changing a selection invalidates old observation identity. Every captured root remains an observation/export obligation.
- Consumption rederives the owner selection, verifies all seven result bindings, and matches exact reaction/action IDs rather than combining every reaction on the same node. It includes the exclusions and selection hash in source proofs. Existing candidate and applied-target freshness checks, including both applied guard invocations, are preserved.
