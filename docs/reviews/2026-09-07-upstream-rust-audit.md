# Pinned figma-mcp-rust feature and utilization audit

Audit date: 2026-09-07. Upstream pin: `6094566436577b29d04393c774d51492c12671e1` (release v0.2.0). Observed local HEAD: **the same commit**. Upstream content was read with `git show <pin>:<path>` in `code-kb/figma-mcp-rust`; no fetch, checkout, source edit, browser operation, or staging change was performed. Service comparisons refer to the current working tree, including existing changes, rather than assuming that HEAD represents it.

The corrected product scope is acknowledged: **only C4 is frontend-only**. C2 and C3 must learn the relevant complete legacy/reference system and implement the portal layers needed for a functioning result, including backend/API/data/authentication where required. This audit does not carry forward the earlier all-cases frontend restriction. It audits the Rust upstream only; conclusions about the other two upstreams require their separate audits.

## Verdict

**All 73 Rust tool names are represented, but not all Rust features are behaviorally preserved, integrated into workflows, or live verified.** A claim that all features of all three original projects are fully utilized would therefore be unsupported even before considering the other two audits.

The current service is a TypeScript implementation with a canonical contract, largely inherited from Figwright, plus selected Rust-inspired adapters and new service controls. It is not the Rust server and plugin shipped unchanged. Its stricter authority, result schemas, write policy, authenticated bridge, and evidence requirements are intentional product changes. Missing behavior must be distinguished from those changes rather than silently counted as parity.

## Concrete behavioral differences and gaps

### P1: Token export loses local paint-style tokens

Pinned upstream `plugin/src/read-styles.ts:181–267` reads both variables and local paint styles. The paint-style reads and exports appear at lines 185, 210, and 248, in CSS and JSON paths. The corresponding tool description includes variables and paint styles.

At the **initial, pre-adoption working-tree observation**, service `service/packages/mcp/src/tools/safe-union.ts`, `handleExportTokens`, called only `get_variable_defs` and derived JSON/CSS from the returned variables. No `get_styles` call or paint-style token merge occurred. Its JSON preserved all variable modes and aliases, and its CSS supported selecting a mode, resolving aliases, avoiding invented FLOAT units, escaping strings, and warning on collisions. These were useful improvements, but **a paint-style-only legacy design could produce no exported tokens**, unlike upstream. This finding describes the source before the main agent's implementation work reported below.

Required decision: restore paint-style export with an explicit provenance/name/collision contract, or declare that subset unsupported. Add variables-only, styles-only, and mixed variable/style fixtures. Existing four `safe-union.test.ts` tests do not contain a paint-style export fixture. This matters directly to legacy C2 and reference-based C3 because those systems may predate variables.

### P1: NOISE effects are not available through the canonical write schema

Pinned `src/tools/definitions.rs` explicitly describes NOISE support for `set_effects`; `plugin/src/write-effects.test.ts:109–144` includes MONOTONE, DUOTONE, MULTITONE, and default noise fixtures. Service `service/packages/mcp/src/tools/effect-schema.ts:17` limits the effect type enum to DROP_SHADOW, INNER_SHADOW, LAYER_BLUR, and BACKGROUND_BLUR. `set_effects` and `create_effect_style` use that schema.

This is a real unsupported subtype, not just renamed arguments. Restore a validated NOISE subtype and supported-API tests if exact design authoring parity is intended, or mark it as an explicit unsupported/beta capability. No evidence inspected establishes that this omission was a deliberate product rejection.

The 43 `adapter` labels must not be treated as evidence that a Rust compatibility shim exists. For example, upstream `batch_rename_nodes` accepts find/replace, regex, prefix, and suffix operations, while service `batch-rename-nodes.ts:8` takes explicit `{nodeId,name}` rows. Prefer explicit composition where appropriate; record any loss of atomicity and require the same admission, policy, and evidence path for each mutation. Do not copy an upstream skill verbatim if it issues a payload the canonical tool rejects.

### PDF capability is implemented, with a new contract

Pinned `src/tools/special.rs:293–375` asks the plugin for page PDFs, merges them through `src/pdf.rs`, and exclusively creates `outputPath`. The service's `safe-union.ts`, `handleExportFramesToPdf`, calls `export_pdf` for each node in bounded pairs, validates node identity and input limits, and merges through `execution/pdf-merge.ts` using `pdf-lib`. It accepts `outPath`, requires 1–256 single-page inputs, preserves requested order, and creates the complete output through `AtomicWritePort`.

The focused test actually exercised a two-page merge, order, wrong-node rejection, and multipage-input rejection with generated PDF fixtures. This supports selected local behavioral tests; it does not prove live Figma export parity, complex PDF fidelity, font handling, or all upstream PDF edge cases. Both Rust-only tool names (`export_tokens`, `export_frames_to_pdf`) are documented in `service/docs/operations-ko.md:42` but neither is mentioned in the currently packaged service skill Markdown. They are available optional tools, not demonstrated automatic steps of the portal-generation workflow.

## Actual workflow use and verification

`service/packages/cli/src/desktop-reader.ts:45–92` calls metadata, selection, one of document/design-context/node, styles and variables. Optional repository analysis adds analyze_project, scan_components, component_map, token_map and icon_map, which are not additional Rust-origin names. Browser/Scripter capture is an independent collection path, not evidence that the Rust plugin executed. Current `figma-codegen` guides a coding agent through grounding/mapping/assets and then says to emit code; it is not a complete portal backend/API/data/auth generation executor.

Consequently, C2/C3 full-system learning and working-portal implementation cannot be established by this 73-tool coverage count. The new plan must separately define full repository analysis, backend/API/data/auth adapters, dependency and runtime contracts, implementation execution, and integrated validation. The Rust Figma bridge contributes design knowledge and manipulation; it does not itself supply all those application layers. C4 can retain the frontend-only restriction.

Historical evidence was examined without re-running browser activity. `docs/reviews/2026-09-05-browser-validation.json` records an existing-Chrome/Scripter collection of 3,198 nodes across 11 sections and explicitly records Desktop live validation as blocked. `docs/reviews/2026-09-06-validation.json` records source/package verification. Neither record is a 73-tool live behavioral parity matrix. This audit does not infer that every tool was historically untested, only that the inspected records do not establish complete live coverage.

## Required follow-up for an accurate product claim

1. Keep the defensible statement: “73/73 Rust tool names mapped into the canonical service.” Do not replace it with “all upstream features utilized.”
2. Add Rust non-tool surfaces, the 12 prompts and 13 skills, and behavioral subfeatures to the capability ledger. Distinguish an implemented capability from a workflow that selects it and from a verified run.
3. Resolve the concrete paint-style token and NOISE gaps. For convenience contracts, choose tested translation/composition or explicit exclusion; do not silently advertise old payload compatibility.
4. Preserve deliberate security/platform changes: authenticated local bridge, explicit filesystem/network effects, constrained egress, bounded results, and durable mutation evidence. Do not restore unauthenticated remote access merely for upstream parity.
5. Add representative live contract tests with isolated fixtures where permitted, plus per-run selection/provenance. Full C2/C3 portal-layer implementation needs its own evidence and must not inherit C4's frontend-only limit.

## Prioritized adoption recipes for reusable portal workflows

These are implementation-ready adoption tasks, not a request to leave useful upstream work permanently documented as missing. The main agent owns the production changes; this reviewer changes only this report/inventory. Each recipe must become a reusable driver step with canonical tool calls, typed input/output artifacts, and acceptance tests. Documentation is a client-facing entry point, not the execution engine.

Use an application-level `portal-build` driver for C2/C3 and retain a frontend preset for C4. Share versioned design-reading/design-system/content workflows between that driver, `figma-codegen`, and `figma-build`. Expose equivalent reusable MCP prompt entry points where helpful, but build their text from the same workflow definitions so prompts, skills, and actual tool arguments cannot drift. Keep a stable upstream recipe ID plus pinned source reference and a canonical-contract version in each definition. The term C1 below means the appropriate C3 or C4 branch after resolution.

For every reusable step, persist scope/source hashes, observed facts versus assumptions, selected strategy, planned mutations, operation IDs, output hash, validation results, and skip reason when inapplicable. Existing user authorization supplies the allowed scope; do not add a repetitive approval prompt merely because an original skill suggested one. Figma source mutation is not required for ordinary portal implementation: read/derive first, and use authoring mutations only within the user's actual requested scope.
