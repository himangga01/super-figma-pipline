## R1-C01: origin-session equality prevents later owner release of retained evidence

**Trigger.** Create a hold under authentication session A, dispatch and settle the operation, then reopen the MCP session or restart/handover the control leader. Authenticate as the same stable owner under session B and explicitly request release of the original hold, with no remaining dependents.

**Current behavior.** `scope()` compares the original binding's `authSessionId` to the current authenticated scope (`evidence-hold.ts:192-200`). `release()` calls that function before inspecting the retained row (`:413-424`), so the request fails with `RECIPE_HOLD_SCOPE_MISMATCH`. This is a real change of authenticated session, not a hypothetical caller-controlled identity: MCP session derivation includes the MCP session identifier (`principal-derivation.ts:171-177`), and control session derivation includes the leader generation and credential fingerprint (`:180-196`). The owner actor is stable across entry paths (`:161-168`).

Changing the supplied binding to session B cannot recover the hold: the hold ID hashes the complete original binding (`evidence-hold.ts:40-41`), `release()` requires that exact hash (`:420-422`), and operation matching separately checks its recorded origin session (`:208-220`). All rows still marked held enter the retention snapshot (`:465-470`), independently of their age. Production initialization supplies this snapshot to receipt/finalizer compaction and workspace retention (`mcp/src/index.ts:853-877`, `:889-891`). Active holds and reserved bytes remain charged (`evidence-hold.ts:234-256`). A later owner session therefore has no supported release transition, and enough abandoned holds eventually reject new admission with `RECIPE_HOLD_CAPACITY_EXCEEDED`.

**Counterevidence checked.** Exact binding, workspace, operation, schema, receipt, artifact and origin-session checks prevent a different session from silently reusing a write result. Preserve them for consumption and execution recovery. Existing tests reject a wrong actual session on `ensureHeld` (`recipe-evidence-hold.test.ts:238-255`), exercise explicit release and dependency refusal (`:271-289`, `:504-529`), and reconstruct managers/journal/receipt stores (`:576-650`). That recovery fixture keeps the original actor's original session; it does not authenticate under a new generation/session. T09's batch coordination correctly protects live holds and does not provide release migration. Absent, pending and outcome-unknown operations are deliberately unreleasable (`evidence-hold.ts:425-429`; tests `:368-377`, `:685-703`), so mere inactivity is insufficient proof for cleanup.

**Fix boundary.** Separate current owner authorization to release retention from authority to reuse the originating operation's result. Keep the immutable original binding and origin session. Provide a dedicated, explicit, audited owner-authorized release/recovery transition under the existing retention mutex, with settlement and dependency proof. Do not rewrite bindings, reopen released holds, permit cross-owner access, or treat release as successful consumption. A never-dispatched reservation needs an independent durable proof that effects cannot still dispatch; an unknown outcome needs supported resolution before release.

**Meaningful acceptance.** Use real session derivation and the authenticated service route: hold and settle under A, recreate the generation and authenticate the same owner under B, explicitly release, and prove active quota and sweep membership change while original operation evidence remains immutable. A different owner, wrong workspace, changed binding, dependent hold, running operation or unresolved outcome must remain rejected. Verify that session B still cannot silently replay a write or use session A's result as its own execution authority. Exercise release concurrently with a retention batch and restart after release publication.

## R1-C02: non-solid paint opacity disappears from full public grounding

**Trigger.** Read two otherwise identical gradients with paint opacity 0.2 and 1 through `get_design_context` at full detail. The same issue applies to IMAGE/VIDEO and PATTERN paint opacity; node-level opacity can remain 1 throughout.

**Exact production path.** The registered server adapter enters `handleDesignContext` (`mcp/src/index.ts:611-619`). The handler defaults to full detail and dispatches the plugin read (`mcp/src/tools/design-context-guard.ts:250-258`). The plugin's full branch always calls `dedupeStyles`, even when component deduplication is disabled (`plugin/src/handlers/get-design-context.ts:784-790`). The shared paint contracts carry gradient, other-paint and pattern opacity (`shared/src/serialized-node.ts:61-67`, `:76-88`, `:96-105`). `simplifyPaint` preserves stop colors/transform, fit/filter markers or pattern geometry but never reads paint opacity in those branches (`design-context-dedupe.ts:80-100`). `dedupeStyles` registers this simplified value and deletes the original `fills`/`strokes` arrays (`:170-177`). The two gradients therefore produce identical style values and the same content-derived reference; callers cannot recover their different effective alpha from the returned full tree. Text-segment paints and collapsed-instance paint overrides also use this simplifier (`plugin/src/handlers/get-design-context.ts:209`, `:497-501`).

**Observable consequence and scope.** Code generation or a consumer of the full design tree may reproduce an opaque gradient/image/pattern when the design uses a translucent paint. Style identity and diffing based on that projection can also collapse distinct appearances. This finding proves paint-opacity loss on the public plugin view. It does not claim that the separate admitted portal raw collector drops that value, or that every aspect of the older broad FID-1 accusation was reverified.

**Counterevidence checked.** Solid paint opacity is folded into hex alpha (`design-context-dedupe.ts:78-79`), gradient-stop alpha survives (`:81-84`), and node-level opacity remains separate. Those values do not replace the missing gradient/image/pattern paint multiplier. The inspected tests cover solid opacity, gradient direction/stops, image fit/filter markers and pattern geometry (`shared/test/design-context-dedupe.test.ts:37-148`), but all non-solid examples use paint opacity 1. Existing bundle-binding tests deliberately drop per-object variable bindings (`:281-334`); that design decision does not justify silently dropping paint alpha. Full tool descriptions direct callers to the full grounding result without an opacity-loss warning (`mcp/src/tools/get-design-context.ts:11-31`).

**Fix boundary.** Carry normalized non-solid paint opacity in the simplified public type and value, or multiply it into every gradient stop while preserving equivalent compositing semantics. Keep image/pattern opacity as a separate paint property; applying it to the whole node would also fade unrelated fills, text or strokes. Update result schema, style identity and consumer projection together. Preserve a raw authoritative projection for consumers that require exact reconstruction.

**Meaningful acceptance.** Exercise the real plugin full handler and canonical runtime result validation with identical gradient/image/pattern paints differing only in opacity. The returned contract must preserve distinct appearance and distinct style identity. Include translucent gradient stops multiplied by translucent paint opacity, multiple stacked fills, full nodes, text segments and collapsed-instance overrides. Verify that solid-alpha handling, component deduplication, token lookup and payload-budget fallback remain correct. Do not replace this with a screenshot-only assertion or a test that merely copies the implementation's output.
