## R2-C01: preparation capacity has no supported reclamation lifecycle

**Trigger and trace.** A single owner creates 32 distinct current portal plans in the same state root, then cancels the runs or otherwise ends their dependencies. The next distinct preparation is rejected with `CORE_PREPARATION_CAPACITY_EXCEEDED`; 128 distinct preparations similarly exhaust the global record limit. Byte limits can also reject admission. The production coordinator uses `plan.planId` as the preparation intent (`core-lifecycle.ts:223`) and always prepares current captured plans before publishing their bound blueprint (`coordinator.ts:989`). Production construction uses the defaults (`index.ts:702`). Capacity rows are appended at `core-preparation.ts:270` and never removed; the only writers found by repository search are its reservation create/update calls. `cancel()` changes preparation status, and `setDependency()` changes only dependencies. Coordinator cancellation releases both plan and run dependencies (`coordinator.ts:468`) without reclaiming the charge.

**Service consequence.** Ordinary repeated planning eventually prevents further coding leases even when there are no live dependents. This is separate from the native environment attempt limit: repairing native attempt reclamation does not restore core preparation capacity. Reusing the exact intent supports interrupted adoption, but it cannot substitute for a new plan whose input or capture has changed.

**Counterevidence.** Permanent charging is deliberate in the source comment at `core-preparation.ts:353`. The complete preparation tests explicitly assert that cancellation does not free capacity. Reservations precede publication, preserve interrupted prefixes and bind the exact owner, workspace, intent, context and input. Signed legacy reconstruction and orphan/adoption tests demonstrate why deleting cancelled rows or merely decrementing counters would be unsafe. Retained bytes still exist, and historical plans may still reference their signed pages.

**Safe fix.** Add an explicit owner-authorized, dependency-aware archival/reclamation lifecycle with durable cleanup intent, actual physical accounting and preserved signed audit/receipt identities. Prove that every plan/run/consumption/receipt dependency has ended or has a durable replacement authority. Interrupted, orphaned or outcome-uncertain publication remains charged until its eligibility is proved. A cancelled status alone is insufficient. Main incorporated this extension into M04 during this review.

**Meaningful tests.** Exercise more than 32 distinct owner plans and more than 128 global preparations through production planning after eligible reclamation. Verify old receipts or explicit archived/replan state, retained in-use and recoverable orphan records, cleanup interruption/restart, concurrent admission/reclaim, ownership rejection and accurate row/byte accounting. Preserve existing cancellation-retention and identical orphan-adoption regressions.

## Safe plan revisions

**M05: review and register the complete prepared value.** Repairing endpoint fields alone leaves the CLI broken. `admin-commands.ts:127` emits authority fragments and `:148` shows the original command list; `:158` instructs the owner to copy selected fragments. Preparation can add preview/consumption commands and assertions. The reviewed/persisted object must be the exact canonical prepared public value, with sensitive environment values handled under existing disclosure authority, and the administrative nonce must bind that exact semantic body. Cover both recipe use and observation manifest, command additions, all authorities and authenticated ownership. Version the contract or explicitly fence/reprepare old persisted profiles instead of silently reinterpreting them. Main incorporated these details into M05; the general plan versioning rule already existed.

The meaningful acceptance is the real public prepare → serialized args file → CLI review → exact confirmation → register path, with no execution during preparation/registration. Tampering with commands, environment, closure, manifest, recipes, source or plan must fail. The targeted CLI tests mock HTTP and check fragments, so they do not close this gap.

**M06: retain proof authority through the actual worker channel.** The existing verifier compares exact check identities, hashes, actual material, dependency perturbation/restoration, resource bytes and source component identity. Wiring it to untrusted model declarations or stdout JSON would create a false completion route. Bind authenticated observations and their receipt to run/candidate/source/plan/preparation/environment/command/output, preserving distinct candidate/applied acceptance. A complete C4 workflow must validate, apply, validate the applied target and complete through supported APIs. Missing, forged, stale, reordered and mismatched observations remain blocked; operational C2/C3 still require their relevant complete portal layers.

**M09: repair identities without weakening incompleteness.** Keep display names as labels and qualify reuse obligations by their exact mapping/source identity. Preserve deterministic replay, same-source and cross-source cases, member paging and deliberate duplicate rejection. Scanner changes must distinguish supported absent props from unresolved imported types and nonexhaustive rest props; no empty/subset API should become completion evidence merely to unblock preparation.

**M12: keep generic/canonical boundaries explicit.** Non-solid paint opacity needs independent identity; changing stop alpha or node opacity is an incorrect repair. Reaction write support must be closed and complete for advertised shapes, with zero writes on unsupported input. Add read → write → read keyboard/overlay/conditional tests and gradient/image/video/pattern opacity separation. Existing canonical capture fidelity is counterevidence to a broad all-path loss claim. Mixed inverse repair still needs exact range restoration or a read-only preflight rejection, not success inferred from nonthrowing undo. Live Figma validation remains necessary beyond mocks.

**M13: propagate relevance to every authority stage.** Changing only the preview interaction contract leaves core derivation blocked. `core-derivation.ts:620` publishes blocking issues and `:627` mandatory obligations; `core-preparation.ts:451` requires all seven results ready. Relevance decisions must affect the signed core input/context, derived pages/results, plan/blueprint, preview manifest and consumption coherently. Keep the full admitted source/root evidence and make exclusions visible and owner-bound. The full core recipe suite explicitly rejects caller-required-root subsets as an omission mechanism. Main incorporated scope propagation into M13. Preserve the original-copy asset route and original digests while providing bounded response previews; expanding analysis response limits alone is insufficient.
