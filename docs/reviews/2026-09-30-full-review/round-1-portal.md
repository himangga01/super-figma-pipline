# Round 1: portal execution, publication and recovery

Date: September 30, 2026. Reviewer lane: portal. Baseline: `db821db346e7cb5dd27e4df465b91bb106e2f2b3`.

The native owner flow cannot currently reach completion. Profile preparation does not round-trip through registration, and the native acceptance producer never supplies the mandatory recipe-consumption receipt. Separately, ordinary run updates exhaust the default retained-generation limit. Recovery defects remain behind those blockers; fixing registration alone would expose them.

This is a static review. I read all 25 assigned production files, all 20 assigned first-party TypeScript test/fixture files and the package fixture completely. The generated lock fixture received metadata, dependency-pin and baseline-hash inspection. All 47 assigned files match the source-manifest hashes. No tests, builds, installation, native helpers, browser, daemon or Docker operation was executed. Test assertions below are inspected source evidence, not results from this review.

## R1-P01: prepared native profiles do not survive the owner registration contract

**Trigger and consequence.** The owner calls the preparation endpoint, reviews its result, obtains the registration nonce and sends that result to registration. The endpoint returns only schema/source versions, plan/context, native configuration, source reviews and assertions (`control.ts:89-97`). It drops the prepared `recipeUse`. For preview profiles it also cannot carry the prepared `observationManifest`, because the strict registration schema lacks that field (`native-work.ts:164-175`). The re-preparation/hash comparison then rejects the registration with `PORTAL_PROFILE_PREPARATION_CHANGED`; restoring only recipe use still cannot transport the required observation manifest. Validation requires a registered profile (`native-work.ts:438-440`).

**Root cause and counterevidence.** `prepareProfile` produces both fields (`native-work.ts:986-1023`), and the persisted profile schema accepts both (`native-work.ts:103-104`), while `assertPreparedProfile` compares the complete prepared authority (`native-work.ts:1025-1033`). The registration schema already accepts `recipeUse`; the defect is its omission from the returned object plus the absent manifest field, not a blanket absence of recipe support. Registration also legitimately rejects blocked consumption preparation (`native-work.ts:822-824`). Bypassing the owner endpoint with a full in-process prepared object can avoid part of this problem, but does not establish that the supported owner workflow works. `native-work.characterization.test.ts:203-273` describes the current error paths.

**Fix boundary and acceptance.** Store an immutable, owner-bound prepared profile and register its reviewed hash, or make every prepared authority field round-trip exactly through the public contract with appropriate payload bounds. Retain source/candidate/closure, owner, nonce, expiry and consumption readiness checks. Exercise the real prepare/nonce/register endpoints for a valid full preview profile, then validate using the persisted profile. Reject omitted, stale, tampered and foreign preparation hashes. Do not use a signed-store seeding seam as the successful acceptance path.

## R1-P02: the native report producer cannot satisfy recipe consumption

**Trigger and consequence.** A registered profile executes successfully and returns an otherwise complete candidate or applied acceptance report. The builder (`native-work.ts:677-758`) never includes `recipeConsumption` or a receipt-derived required consumption check. The completion gate requires a receipt bound to the owner, workspace, context, blueprint, candidate, declarations, target, verifier and results (`ir/src/portal-run.ts:223-240`). The coordinator therefore returns `blocked` instead of `ready-to-apply` or `completed` (`coordinator.ts:1588-1600`); apply independently enforces this gate (`native-work.ts:1493-1498`). This is an independent blocker after R1-P01, rather than evidence that the current public registration path reaches validation.

**Root cause and counterevidence.** Preparation compiles and attaches consumption batches (`native-work.ts:986-988`), and the owned browser computes actual consumption observations (`preview.ts:578-591`). The producer never calls `verifyConsumptionObservations`; its production definition is in `recipes/core-consumption.ts:856`, with no production caller found. These existing observations are useful inputs, not the required verified receipt. `native-work.characterization.test.ts:277-327` deliberately seeds the signed profile that R1-P01 prevents the owner from registering and asserts this missing-receipt failure.

**Fix boundary and acceptance.** Verify owned consumption observations against the current core input and attached declarations, and include the resulting target-specific receipt and check in the stored acceptance report. Fail closed for missing or mismatched evidence. A real preview must produce a valid candidate receipt that passes the candidate gate, followed by a separate applied receipt that passes applied completion. Missing, failed, duplicate, forged, wrong-owner, wrong-source and wrong-target observations must block. Preserve the existing gate; do not weaken it to accommodate the incomplete producer.

## R1-P03: retained generations impose a permanent 64-update ceiling

**Trigger and consequence.** `PortalStore` creates its atomic store without raising or collecting the normal retained-generation budget; only recipe holds and environment records receive special budgets (`store.ts:120-149`). `AtomicFileStore` defaults to 64 retained replacements per target (`atomic-file.ts:1927-1930`) and rejects the next prospective replacement (`atomic-file.ts:2054-2070`). Each `portal_next` mutates the run, including an evidence/renewal call (`coordinator.ts:1194`; version increments at `1145`). After 64 replacements, later next/resume/cancel state writes remain impossible. This is reachable without native registration.

Publication additionally records an intent and a written observation per file (`native-work.ts:1676-1680`, `1695-1698`), then an applied state (`1700-1703`). A new target also saves its root identity (`1607-1610`). Thus a fresh legacy journal needs `2N+1` replacements and a new-target journal needs `2N+2`; a 32-file publication exceeds the default cap. Source writes may already have occurred when the journal fails, and continuation encounters the same exhausted budget. This portion is latent behind R1-P01/R1-P02.

**Counterevidence and fix boundary.** The limit is per atomic target, not 64 total records across the store. Create-only plans are not implicated. Larger byte budgets and special environment-record budgets do not fix ordinary run/apply history. `store.characterization.test.ts:31-57` explicitly expects 64 successes and the 65th failure; it does not show recovery. Implement bounded collection of proven obsolete generations or a recoverable journal with bounded checkpoints. Preserve committed state, pending recovery evidence, exact preimages and unknown-artifact fencing; merely raising caps or deleting every sidecar is insufficient.

**Acceptance.** Hundreds of evidence/renewal calls followed by cancellation and restart must remain writable. Publish at least 300 files, inject interruption at atomic replacement and journal boundaries, and resume safely. Preserve user edits and unknown sidecars while demonstrating that retained row/byte/scan usage stabilizes.

## R1-P04: an attempt creation gap quarantines the whole native environment indefinitely

**Trigger and consequence.** Acquisition records `creating`, creates the actual directory, secures it, observes its identity, and only then saves that identity (`native-lifecycle.ts:203-213`). An error or process death between `mkdir` and durable identity persistence leaves a real directory with `directoryIdentity: null`. Error handling quarantines it (`245-248`). Every later acquisition runs retention inspection (`129`); a present retained directory without the saved identity throws `PORTAL_ENVIRONMENT_RETENTION_RECONCILIATION_REQUIRED` (`306-309`). The owner's reconcile path ultimately requires the missing identity through `verifyDirectories` (`413-418`, `508`, `556-568`), so it rejects with `PORTAL_ENVIRONMENT_DIRECTORY_CHANGED` rather than restoring usable admission.

**Counterevidence.** Refusing to adopt or delete an arbitrary same-path directory is correct. This finding is the absence of a bounded recovery outcome and the propagation of one unbound attempt into a shared admission fence, not a request to relax identity checks. `native-environment.test.ts:472-510` injects identity-persistence failure, inspects quarantine and expects reconcile to reject. It proves the conservative fence in its source assertions, not recovery. This path is latent until native work can be admitted.

**Fix boundary and acceptance.** Persist a creation intent and support narrowly authorized orphan resolution while retaining proof about namespace, owner, process absence, resource claims and unknown identity. Scope an unresolved orphan so unrelated attempts can proceed when capacity and resource safety are demonstrable; otherwise provide an explicit actionable recovery outcome. Fault-inject each boundary from directory creation to identity commit and restart. The owner must obtain a supported safe outcome, a substituted directory must remain untouched, and an unrelated admissible run must not remain permanently wedged.

## R1-P05: released native attempts accumulate to a terminal admission ceiling

**Trigger and consequence.** Each attempt ID is appended to a signed retained index, whose source comment explicitly says it is an admission ceiling rather than a collector (`native-lifecycle.ts:123-143`). No release/reconcile path removes an ID or reclaims its directory. Reservation 129 is rejected by the 128-entry ceiling. Earlier failure is possible because every admission traverses retained directories and rejects above 200,000 entries or 8 GiB (`277-311`), including dependency trees. Failed and released attempts still consume capacity; the exact number of realistic Vite attempts before byte/entry exhaustion is not statically established.

**Counterevidence and fix boundary.** Retention supports receipt verification and protects uncertain processes/resources. The per-record 512-generation environment allowance addresses a different limit and does not reclaim this index. The earlier estimate of approximately ten validations is not accepted as a proved threshold here. Add explicit evidence holds, release eligibility and bounded collection for proven closed, unheld attempts, with versioned accounting and a recoverable collector. Do not delete the oldest directory unconditionally or release claims merely because the service restarted. Core-preparation retention belongs to the recipes lane and is not fully assessed here.

**Acceptance.** Run more than 128 small completed native attempts and enough larger dependency attempts to exercise entry/byte limits; verify steady-state admission and bounded scan cost. Active, unknown-process, identity-mismatched and held evidence directories must survive. Receipt access after collection must follow an explicit retention/expiry contract. This is a latent operational failure behind the registration blocker.

## R1-P06: resume without reconciliation can overwrite active cancellation and validation

**Trigger and consequence.** `portal_resume(reconcile: 'none')` is excluded from the coordinator's active-operation reservation (`coordinator.ts:375-379`). Its mutation rejects applying/outcome-unknown/conflict and terminal states but accepts `cancel-requested` and `validating-*`, clears the lease and resets state to waiting/candidate-ready/applied-awaiting-validation (`552-566`). While cancel is suspended after writing `cancel-requested` (`446-459`), resume can reset that state; cancel's final mutation only finalizes a still-cancel-requested run (`463-466`). The persisted run is then available for new generation rather than durably cancelled. During validation, resume changes the version, causing `PORTAL_VALIDATION_SUPERSEDED` (`1584`); error cleanup changes only a still-validating state (`1606-1609`), leaving the reset state and discarded report.

**Production counterevidence.** The queue does not serialize these operations by run identity: resume uses `portal:run:<run>` while validation owns `portal:process:<run>` plus repository read (`coordinator.ts:333-345`; `native-resources.ts:349-350`). The executor uses those explicit resources (`execution/operation-executor.ts:1542-1554`). Cancellation uses an independent control key (`coordinator.ts:294-306`). Existing owned-operation and native-job busy maps fence a second owned native operation, and cancel aborts the current operation; neither fences this resume mutation. Completed cancellation is terminal and cannot be resurrected. The race is specifically the in-progress interval, not any later resume of a cancelled run. Cancellation without native execution is currently reachable; the validation branch is latent.

**Fix boundary and acceptance.** Fence state mutation against live operation and cancellation epochs under the same durable compare-and-set protocol. Resume-none must reject live validation and cancellation, with a separate explicit recovery path for a crashed operation whose absence has been proved. Pause cancel after its request commit and validation after admission; issue resume through the production resource queue. Cancellation must remain final, no new lease may become valid, and active validation must not be superseded by resume. Restart recovery must still distinguish a crashed operation from a live one.

## R1-P07: new-target publication exposes an unbound directory before durable identity

**Trigger and consequence.** The new-target journal starts with `targetIdentity: null` (`native-work.ts:1552-1573`). Apply creates the final visible target root (`1601`), marks the local outcome committed, obtains identity and then saves it (`1602-1610`). A store failure or process death before that save leaves the final directory present but unbound in the durable journal. Retry rejects the existing path with `PORTAL_TARGET_IDENTITY_RECOVERY_REQUIRED` (`1587-1594`), while inventory/reconciliation requires a saved target identity (`1405-1409`). There is no supported proof-based recovery of this interval. Subsequent file publication is also performed individually into this visible root rather than publishing the completed tree at one no-replace commit point (`1613-1698`). The active plan requires same-volume no-replace publication (`docs/plans/2026-09-07-portal-four-cases-plan.md:137`).

**Counterevidence.** Empty-directory collision rejection, retained ancestor checks, exact file preimage CAS and later target-identity checks correctly protect existing or replaced directories. The current test that substitutes a same-byte new target confirms why automatic same-path adoption would be unsafe. These checks do not bind the run-created directory before its first visible side effect. The failure is latent behind acceptance blockers and distinct from R1-P04's environment namespace.

**Fix boundary and acceptance.** Prepare and identity-bind the complete target in a retained same-volume staging directory, record the publication intent and use no-replace final publication with an explicit durable commit/recovery observation. Preserve collision and replacement fences. Inject failure before/after publication and before its observation commit, then restart: infer only publication of the bound tree or safely retry. A substituted directory and an existing empty destination must remain untouched, and consumers must not see the partially generated final tree.

## R1-P08: a preflight-only apply error becomes an unrecoverable conflict

**Trigger and consequence.** The coordinator commits `applying` before invoking native work (`coordinator.ts:1615-1629`). Native apply can reject validation/environment/source/authority/preimage or target-collision checks before creating any journal (`native-work.ts:1493-1550`). The coordinator maps any error without a truthy `committed` flag to `conflict` (`coordinator.ts:1653-1657`). Resume-none refuses that state (`554-555`), and resume reconciliation requires an apply record that does not exist (`native-work.ts:353-354`). Thus even a proved pre-mutation failure, including cancellation before native work begins, has no supported retry/reset outcome for that run. This is latent behind R1-P02.

**Counterevidence and fix boundary.** Conservative conflict for uncertain source effects is correct, and an existing journal can reconcile preimage/candidate/conflict states. The missing distinction is an explicit no-source-mutation outcome before journal creation; absence of a boolean alone is not that proof. Return a typed mutation outcome or establish a durable preflight intent so the coordinator can restore a recoverable blocked/ready state when non-application is proved. Leave uncertain effects in inspectable conflict/outcome-unknown states.

**Acceptance.** Inject each preflight rejection and cancellation before journal creation, verify unchanged source and no journal, correct the recoverable cause and retry the same run. Repeat with interruption after intent/source publication and ensure that uncertain outcomes still require reconciliation and preserve concurrent edits.

## R1-P09: the generation deadline also disables post-publication validation and recovery

**Trigger and consequence.** Start sets one absolute deadline one hour later (`coordinator.ts:1121`). Both candidate/applied validation and apply use it (`native-work.ts:328-340`); `owned` refuses work after it expires and aborts work at the same deadline (`274-280`). Resume-none also refuses expired runs (`coordinator.ts:557`). If generation and candidate validation use most of the hour, publication can leave an applied-awaiting-validation target with no remaining ability to perform applied validation. A partial publication may be inspectable, but resume-continue invokes the same expired apply budget (`coordinator.ts:506-517`). No deadline-renewal transition is present. This is a latent recovery limitation, not a claim that an already completed run becomes invalid later.

**Counterevidence and fix boundary.** Absolute deadlines and cancellation are valuable, and inspection can be allowed without reopening effects. Simply widening the global timeout would retain the problem. Define separate bounded generation, validation, publication and recovery budgets, with durable admission/remaining-work policy and explicit total limits. Expiration must not strand already published source without a supported bounded applied-validation/reconciliation route.

**Acceptance.** With a controlled clock, finish candidate validation near the generation deadline, apply, advance beyond it and complete applied validation under the authorized effect budget. Restart partial publication after generation expiry and safely continue or produce an explicit supported recovery result. Hung commands and exhausted effect budgets must still terminate with proved process cleanup.

## R1-P10: failed visual checks discard the structured repair evidence

**Trigger and consequence.** The browser assembles reports containing screen results and consumption observations (`preview.ts:585-604`) but throws `PORTAL_PREVIEW_FAILED` before returning a failed-screen report (`607-609`). The owned worker calls it with stdout reporting disabled and only emits its authenticated receipt after a successful return (`preview-worker.ts:183-203`); its bootstrap failure path emits the error code (`65-66`). The runner consumes that receipt only on passed commands and closes the channel otherwise (`native-runner.ts:432-435`). Portal feedback exposes the final four command outputs (`coordinator.ts:1524-1538`) without the structured failed-screen comparison, image/diff references or measurements. The most useful repair case therefore loses the evidence that a successful preview would retain. This is latent until a valid preview profile can be registered.

**Counterevidence and fix boundary.** Actual screenshot/diff files may remain inside the retained attempt, but the supported feedback contract does not return their failed report. Disallowing stdout as authority and keeping per-candidate owner approval are sound; the latter is a deliberate decision, not this finding. Extend the authenticated receipt protocol to carry bounded failure evidence, persist it regardless of pass/fail, and expose source-bound failed observations in feedback without counting them as successful acceptance.

**Acceptance.** A real visual mismatch must return blocked validation plus the actual failed observation ID, candidate hash, comparison measurements and accessible screenshot/diff evidence through `portal_next`. Forged stdout or another attempt's receipt must not create authority; output/redaction bounds and failed consumption/check semantics must remain enforced.

## Service assessment and invariants to preserve

The current plan and analysis represent the right case split: C4 is frontend-only; C2/C3 retain applicable frontend, backend, API, database, authentication, authorization, job, storage and integration work. The production completion path cannot demonstrate any of those full cases while R1-P01/R1-P02 remain. Native operational tests describe useful actual HTTP/SQLite fixtures, but their registration/acceptance seams do not prove a complete C2/C3 owner workflow. C1 must continue inheriting the selected C3/C4 strategy rather than becoming a separate weaker acceptance mode.

Source and publication checks have meaningful protections: owner-bound signed records; version-2 source authority and rejection of stale effect authority; complete material candidate/baseline closure; source revalidation around execution; exact preimage CAS; target identity fencing; and inspectable partial outcomes. Recovery must preserve concurrent edits and unknown artifacts. I found no justification for reset/stash/index rewrites or for pretending that database effects can be rolled back with repository files.

Native execution records filtered environment, pinned executable/script/artifact/module authority and owned process membership. The Windows broker permission and stop acknowledgments support conservative cleanup of owned processes. These are same-account filesystem and process protections, not an OS sandbox against malicious same-account code. The review did not execute their runtime proof. Preview uses an owned listener/browser, an independent authenticated receipt channel, image bytes and isolated DOM observation; forged stdout and poisoned page globals are not accepted as authority. Preserve these properties when adding failure receipts and consumption completion.

## Inspected tests and coverage limits

All assigned tests were read, including coordinator cancellation/reconciliation, source authority/closure/CAS, native artifact/module fences, Windows environment/process proof, preview leases/channels/consumption/interaction, native work and native HTTP/SQLite fixtures. Useful negative tests cover stale grants, swapped directories, forged receipts, cancellation, changed source, malformed artifacts and unsafe native processes. Their existence is not a passing result from this review.

The SVC-1/K1 and 65th-replacement characterization tests intentionally assert defective outcomes. The creation-gap environment test intentionally asserts quarantine and failed reconcile. Several broader native-work tests construct acceptance fixtures without the currently mandatory recipe-consumption receipt, so they can stop at `PORTAL_VALIDATION_REQUIRED` before their intended publication/recovery assertion. Direct in-process registration and signed-profile seeding are narrower seams than the owner workflow. None should be presented as completed case acceptance. Gated real Vite tests were inspected; whether CI enables and passes them belongs to the verification lane.

The coverage JSON records all assigned paths and targeted cross-lane reads. The generated lockfile was not read line by line. The large active plan and historical remediation documents were read in relevant sections; cross-lane source inventory, source policy, service graph, recipe verifier, completion contract and atomic-store contracts were targeted rather than exhaustively reviewed. No browser fidelity, Windows locale behavior, process cleanup timing, resource saturation or native-toolchain success was verified here.

Two scope questions need targeted follow-up, without treating them as proved additional blockers. `preview-listener.ts:20` parses the English `LISTENING` state; locale-dependent impact requires native evidence, and the T01 Unicode broker fixes do not by themselves establish it. `native-resources.ts:216-223` defaults every profile to an owned SQLite grant and `native-lifecycle.ts:214-229` provisions it, including C4. The active plan forbids backend-only operations in C4 (`docs/plans/2026-09-07-portal-four-cases-plan.md:129`). Confirm whether this is deliberately a verification harness resource; if it is unnecessary for C4, allow a database-free native environment without weakening C2/C3 workflow resource checks. No unsupported claim about a generated C4 application backend is made here.

## Recommended order

Fix the prepared-profile contract and consumption producer together with a real owner-flow acceptance test. Address retained state capacity before attempting large or repeated acceptance runs. Then fence resume/cancellation and implement bounded native-attempt/new-target recovery with identity proofs. Separate preflight outcomes and effect/recovery budgets, and preserve structured failed-preview evidence. Finally execute native, restart/fault, repeated-attempt and complete C2/C3/C4 acceptance in the authorized separate working copy. The September 27 characterizations should be retained as historical evidence and replaced or supplemented with passing product acceptance for each fixed path.
