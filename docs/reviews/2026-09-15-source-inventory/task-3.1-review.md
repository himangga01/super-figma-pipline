## Consumer-contract observations

These observations identify the exact meaning of the new fields. They are not findings that require changes before Task 3.1 integration.

| Severity | Location | Observation and required interpretation |
| --- | --- | --- |
| Informational | `packages/mcp/src/portal/source-inventory.ts:59`, `:83`; `packages/mcp/src/portal/service-graph.ts:101` | Inventory completeness concerns byte discovery and reading under the recorded policy. A binary `package.json`, `.ts`, `.js`, or `.json` can correctly belong to a complete byte inventory. When such a file is a semantic candidate, the graph omits it from text evidence and emits hard `SOURCE_ENCODING` incompleteness. The focused graph fixture explicitly checks this distinction. Conversely, a legitimate opaque asset need not make the byte inventory or graph incomplete solely because it is binary. The conservative classifier can reject control characters even inside otherwise parseable source comments; that is a documented fail-closed classification choice, not silent byte loss. |
| Informational | `packages/mcp/src/portal/service-graph.ts:71`, `:80`; `packages/mcp/src/portal/source-inventory.ts:31` | Semantic selection remains filtered. Ignored/generated/dot-directory code and unsupported semantic extensions are byte-bound without automatically acquiring parse evidence or an encoding issue. A complete inventory is not a complete parsed import graph, and `graph.incomplete === false` must not be used to infer new semantic coverage for these paths. Broadening inference is explicitly excluded from Task 3.1. Later qualified source delivery must consume inventory membership instead of falling back to the semantic file list. |
| Informational | `packages/mcp/src/portal/source-inventory.ts:87` | The inventory hash identifies the entire recorded discovery result, not just staged source bytes. Limits, `scannedEntries`, exclusion presence/kind, and issues are part of the hash. Adding an empty included directory can change the scan count; omitting `.git`, `.env`, `.sfp`, or `node_modules` from a staged copy changes recorded exclusions and usually scan counts. Identical included file bytes across those trees therefore need not produce equal inventory hashes. This is conservative and consistent with the report; no current Task 3.1 staging consumer was added that incorrectly equates them. |
| Informational | `packages/shared/src/portal.ts:219`, `:278` | Shape validation and optional legacy compatibility do not establish that a stored inventory was freshly recomputed or that staging reproduces its source. Later consumers must enforce supported inventory policy/version and required presence/completeness, bind the recorded original-source identity, and validate staged membership/content against the included file records under an explicit transformation/provisioning contract. They must not copy excluded credentials or metadata merely to make the full discovery hash match. |

## Follow-on boundary

The recorded original-source identity can be revalidated with the same policy and limits against its source tree. Staging needs a separately defined equality check over the intended included bytes and its declared transformations; provisioning and allowed runtime artifacts need their own qualification. Neither this review nor Task 3.1 proves those later contracts.

Discovery and semantic reads are successive retained-authority operations, not an atomic filesystem snapshot. The separate validation copy provides edit separation under the current user's permissions; it does not provide OS, network, account, or process confinement. The connected live daemon and its older primary build remain untouched and are not claimed to run these reviewed bytes.
